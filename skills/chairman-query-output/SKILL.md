# 董事长问数输出

把每次回答当成一份微型决策材料，不当成分析师的过程汇报。

## 工作流

1. 读取问题、QuerySpec、授权范围、工具结果、来源和数据截止时间。只使用可验证证据，不补造金额、概率、责任人或日期。
2. 先判断决策就绪度：`ready`、`conditional` 或 `not_ready`。检查关键字段完整性、来源时效、口径一致性和比较基准；数据问题足以改变结论时，必须出现在第一屏。
3. 从五类模板中选择一个主模板。完整触发条件和字段要求见 [templates.md](references/templates.md)。
4. 按 [chairman-answer.schema.json](assets/chairman-answer.schema.json) 生成结构化结果。模板路由的机器配置见 [template-registry.json](assets/template-registry.json)。
5. 校验结论、证据、动作和视觉。评测题与断言见 [evaluation.md](references/evaluation.md)。

## 模板路由

| 模板 | 主要问题 |
| --- | --- |
| `executive_pulse` | 现在经营状态如何、发生了什么变化、是否需要介入 |
| `target_gap` | 能否达标、缺口多大、靠什么兑现 |
| `risk_action` | 哪些异常最危险、暴露多少、谁负责关闭 |
| `top_opportunities` | 哪些客户或商机最值得亲自跟、集中度和确定性如何 |
| `decision_memo` | 两个或多个事业部、负责人、客户或方案如何取舍 |

若数据不足以支持用户要求的预测或推荐，保留原模板，但把 `decision_readiness` 设为 `not_ready`，将第一句话改成不能决策的具体原因，并输出最小补数动作。不要用泛化免责声明代替判断。

## 第一屏契约

按以下顺序输出，首屏之外的证据渐进展开：

1. `decision_line`：一句有方向的判断，直接回答“要不要介入、追哪件事、暂时不能判断什么”。
2. `metrics`：仅保留 2–3 个能证明判断的数字；每个数字必须带口径或比较基准。
3. `primary_evidence`：最多一个主图或主表。图用于形状和比较，表用于精确查阅；没有合适证据形态就省略。
4. `risks_or_opportunities`：最多三项，按决策影响排序。
5. `actions`：写清责任人、动作、截止时间和复核指标。来源没有责任人或日期时明确写“待指定”，不得猜测。
6. `data_quality`：显示数据截止时间、范围、就绪度、关键缺口和它对结论的影响。
7. `sources`：保留可追溯来源；默认折叠源记录明细，但数据时间和就绪度始终可见。

## 写作规则

- 结论先行，默认 150–350 个中文字；用户明确要求详细报告时再展开。
- 标题写结论或决策任务，不写“数据分析”“关键发现”“数据对比”。
- 区分事实、推断、建议。推断必须写出依据和置信等级。
- 避免“整体向好”“建议关注”“持续推进”等无对象、无尺度、无动作的句子。
- 不把商机金额等同于可兑现收入；没有目标、概率、预计签单时间或历史转化口径时，不输出伪精确预测。
- 动作使用“谁在何时前完成什么，以哪个指标复核”的句式。

## 视觉规则

- 单列阅读流优先，不把回答变成缩小版仪表盘。
- 一次回答最多一个主图；长标签用横向条形，时间趋势至少需要足够的连续观测点，目标缺口优先用进度或差距桥。
- 只使用一个低饱和强调色；风险还要依赖排序、文字、符号和浅底，不能只靠红绿。
- 指标数字使用等宽或等宽数字特性；卡片只在表达层级时使用，不嵌套卡片。
- 图表标题描述指标、范围和时间；结论写在相邻正文，不让图标题承担未经验证的推断。

## 输出前检查

- 五秒内能否复述结论？
- 是否知道董事长需不需要介入？
- 每个关键数字是否有范围、时间和来源？
- 主图是否直接证明结论，且只有一张？
- 是否写清责任人、截止时间和复核指标？
- 数据问题是否在会改变判断的位置出现？
- 是否存在无法证实的预测、赢率、因果或责任归属？若有，删除或降级。
